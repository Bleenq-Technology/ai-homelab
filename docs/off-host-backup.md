# Off-host backups — jarvis → Asustor NAS

True off-site/off-host disaster-recovery copy of the homelab's nightly datastore
backups. Closes the gap called out in [`docker/backup.sh`](../docker/backup.sh) and the
README roadmap: until now the local dumps **and** the MinIO copy both lived on jarvis's
single disk, so nothing survived loss of that disk.

## Architecture

```
jarvis (Ubuntu)                              stor.lab.example  (Asustor AS6706F / FS6706T, x86_64)
─────────────────                            ──────────────────────────────────────────────────────────
/opt/homelab/backup.sh   (cron 0 2 * * *)    ADM 5.1.3 · Docker 28.x · App Central "docker-ce"
  ├─ pg_dumpall / CH BACKUP / QuestDB / MinIO   ┌──────────────────────────────────────────────┐
  └─ backup_offhost():  restic backup  ───────► │ restic/rest-server  --private-repos            │
        $BK = /opt/homelab/backups               │                     --append-only :28000 (HTTP) │
        RESTIC_REPOSITORY=rest:http://jarvis:***@stor:28000/jarvis/   │ repo data → /volume1/Docker/restic-rest/data/jarvis
        RESTIC_PASSWORD=*** (repo encryption)    └──────────────────────────────────────────────┘
                                                  repo data → /volume1/restic-backups/jarvis (shared folder)
```

- **restic** does client-side **encryption** (the NAS never sees plaintext — important:
  the dumps include the Infisical/Keycloak/app Postgres data), **deduplication** (nightly
  near-identical dumps cost ~0 B after the first), and **integrity verification**.
- **`--append-only`**: jarvis can *add* snapshots but cannot *delete* them. A compromised
  or ransomwared jarvis cannot wipe backup history (verified: a delete returns `403`).
- **`--private-repos`**: the `jarvis` account is scoped to the repo path `/jarvis`.
- Transport is plain **HTTP on the trusted LAN/VLAN**. The repo contents are encrypted by
  restic regardless; HTTP only carries the basic-auth credential + already-encrypted blobs.
  *Hardening follow-up:* rest-server supports `--tls` (self-signed) if desired.

## Credentials (all in Infisical `homelab/prod`)

| Var                            | Role                                                                   |
| ------------------------------ | ---------------------------------------------------------------------- |
| `ASUSTOR_HOST_NAME`            | NAS hostname — `stor.lab.example` (resolves to `192.168.2.11`) |
| `ASUSTOR_INTEGRATION_LOGIN`    | NAS account **and** rest-server basic-auth user — `jarvis`             |
| `ASUSTOR_INTEGRATION_PASSWORD` | the NAS `jarvis` account password (SSH / SMB / sudo)                   |
| `RESTIC_REST_PASSWORD`         | rest-server basic-auth password for user `jarvis` (URL-safe hex)       |
| `RESTIC_PASSWORD`              | **repo encryption key** — losing it makes every backup unrecoverable   |

> `RESTIC_PASSWORD` belongs in the **bootstrap set** vaulted in a password manager
> (alongside `INFISICAL_ENCRYPTION_KEY`): if jarvis *and* Infisical are both lost, you
> still need this key to read the NAS backups during a rebuild. See
> [`core/infisical/README.md`](../docker/core/infisical/README.md).

`backup.sh` reads them from `/opt/homelab/.env` (regenerated by `pull-secrets.sh`). To
rotate any of them: set in Infisical (`./push-secret.sh KEY VALUE`) → `./pull-secrets.sh`.
The rest-server user password (`RESTIC_REST_PASSWORD`) is *also* baked into the NAS
`.htpasswd` (bcrypt) — rotating it means regenerating that file too (see below).

## The rest-server container (on the NAS)

Defined at `/volume1/Docker/restic-rest/compose.yml` (managed over SSH; the NAS is **not**
a git checkout):

```yaml
services:
  restic-rest:
    image: restic/rest-server:0.13.0@sha256:8668c235a932745585fef5cabbab9eccb501035f90138085a6e74963dcd1a71f
    container_name: restic-rest
    restart: unless-stopped
    environment:
      - OPTIONS=--private-repos --append-only
    ports:
      - "28000:8000"
    volumes:
      - /volume1/restic-backups:/data               # dedicated shared folder; repo + .htpasswd live here
```

- **Auth gotcha:** do **not** set `DISABLE_AUTHENTICATION` — the image disables auth if that
  var is set to *any non-empty value* (even `false`). Omitting it keeps `.htpasswd` auth on.
- The `restic-backups` shared folder (mounted at `/data`) holds `.htpasswd` (user `jarvis`,
  bcrypt) and the repo at `jarvis/`. The compose file itself lives at `/volume1/Docker/restic-rest/`.
- ADM requires the `jarvis` account to be in the **administrators** group for SSH/Docker
  management. The *backup path itself* only needs rest-server HTTP auth — so once deployed,
  `jarvis` could be dropped from administrators / Terminal disabled and backups still run.

Regenerate `.htpasswd` (e.g. after rotating `RESTIC_REST_PASSWORD`), run on jarvis:

```bash
cd /opt/homelab
RRP=$(grep ^RESTIC_REST_PASSWORD= .env | cut -d= -f2- | tr -d "'\"")
htpasswd -nbB jarvis "$RRP" | ssh jarvis@stor.lab.example 'cat > /volume1/restic-backups/.htpasswd'
```

## Restore runbook

On any host with `restic` + the two repo secrets:

```bash
export RESTIC_REPOSITORY="rest:http://jarvis:<RESTIC_REST_PASSWORD>@stor.lab.example:28000/jarvis/"
export RESTIC_PASSWORD="<RESTIC_PASSWORD>"

restic snapshots                              # list available points in time
restic restore latest --target /tmp/restore   # restore the newest snapshot
restic restore <ID> --target /tmp/restore --include /opt/homelab/backups/postgres-all-XXXX.sql.gz
```

Then restore the chosen dump into the live service the normal way (e.g. Postgres:
`gunzip -c postgres-all-*.sql.gz | docker exec -i postgres psql -U postgres`). A full
DR rebuild also needs the Infisical Postgres DB + `INFISICAL_ENCRYPTION_KEY` — see the
Infisical README "Rebuild from scratch".

## Retention / pruning (deliberate maintenance — append-only)

`--append-only` blocks `restic forget`/`prune` from jarvis **by design** (that's the
tamper-resistance). Data is tiny and deduplicated, so the repo grows slowly; prune only
occasionally, as a deliberate maintenance window:

```bash
# on the NAS, temporarily relax append-only:
sed -i 's/ --append-only//' /volume1/Docker/restic-rest/compose.yml
sudo docker compose -f /volume1/Docker/restic-rest/compose.yml up -d
# then from jarvis, apply a retention policy + prune:
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune
# re-enable append-only (restore the flag) and recreate:
#   OPTIONS=--private-repos --append-only  → docker compose up -d
```

## Operational notes

- No new cron — the off-host step rides the existing nightly `backup.sh` (`0 2 * * *`).
  Failures log `[ERROR] off-host (restic->NAS) FAILED` and (like every datastore) do not
  abort the other backups.
- Sundays the job also runs `restic check` against the repo.
- restic on jarvis: installed via apt then `restic self-update` (0.18.1+).

## Monitoring the backups themselves — and the trap in it (2026-07-18)

`backup.sh` publishes `homelab_backup_*` metrics into node-exporter's **textfile collector**
(`/var/lib/node_exporter/textfile/homelab_backup.prom`); Prometheus alerts `BackupStale` (>30h),
`BackupVeryStale` (>50h), `BackupMetricsMissing` (`absent()`) and `BackupComponentFailed` key off them.

**The failure mode this monitoring can itself produce — and did.** The textfile dir was `root:root
0755` while cron runs `backup.sh` as a **`homelab` user**, so the metric write failed with *Permission
denied* every night from **2026-07-09 to 07-18**. The `.prom` file kept its Jul 9 timestamp and kept
being scraped, so `BackupStale` + `BackupVeryStale` fired **daily for nine days while the backups were
entirely healthy** (snapshots saved nightly, weekly `restic check` clean across 33 snapshots).

Two things made it silent for so long, both now fixed in `backup.sh`:
- `publish_metrics()` only tested `[ -d ]`, not `[ -w ]`. An unwritable-but-present dir is the
  *dangerous* case: `absent()` never trips (the stale file is still there and still scraped), so the
  alert points at the wrong thing entirely.
- The `} > "$tmp" && mv … && chmod …` chain short-circuited on failure, but the following
  `log "metrics: wrote …(all_ok=1)"` ran **unconditionally** — the log actively asserted success it had
  never verified. It now logs `[ERROR] metrics: FAILED to write …` and returns non-zero.

**Required host state** (survives a node-exporter or host rebuild — re-apply if you rebuild):
```bash
sudo chgrp homelab /var/lib/node_exporter/textfile
sudo chmod 2775   /var/lib/node_exporter/textfile   # setgid: both devs' cron can write
```

**Reading the alert correctly:** `BackupStale` means *"the metric is old"*, which is **not** the same
as *"the backup failed"*. Check in this order — (1) `tail /srv/ai-data/backups/backup.log` for an
actual run and a `snapshot … saved` line; (2) `ls -la /var/lib/node_exporter/textfile/` for the
`.prom` mtime. A recent log plus a stale `.prom` means the metric pipeline broke, not the backup.

## Backup sources are resolved from Docker, not hardcoded (2026-07-18)

While fixing the alerting bug above, two backup **sources** turned out to have silently rotted —
both reporting `component_success=1` every night:

| component | script pointed at | service actually used | effect |
|---|---|---|---|
| questdb | docker volume `homelab_questdb_data` | bind `/srv/ai-data/marketdata/questdb` | **every nightly archive was an empty 87-byte tar** — 47 MB of market data had never been backed up, locally *or* off-host |
| minio | `/opt/homelab/data/minio/data` | bind `/srv/ai-data/object-store` | archived a **pre-storage-tiering copy frozen at 2026-06-29** (54 MB) instead of the live store (133 MB) |

QuestDB's is the nastier of the two: `docker run -v <name>:/data` **silently creates** a missing
volume rather than failing, so `backup.sh` manufactured its own empty volume (created
`2026-07-10T02:00:42Z` — a backup-run timestamp) and dutifully archived nothing thereafter.

**The fix — `resolve_mount()`.** Sources now come from `docker inspect` at run time, so the backup
follows the service instead of drifting from it:

```bash
resolve_mount(){  # container, destination-inside-container
  docker inspect "$1" --format "{{range .Mounts}}{{if eq .Destination \"$2\"}}{{.Source}}{{end}}{{end}}"
}
```

**And a real emptiness guard — `tar_host_dir()`.** The old check was `[ -s "$out" ]`, which proves
nothing: **gzip of an empty directory is a valid ~87-byte file**, so the broken QuestDB backup passed
its own check every single night. The archive must now contain **≥2 entries**, and an unresolvable
or non-existent source is a hard failure. Both paths are negative-tested.

**Verified after the fix:** questdb `87 B → 3.7 MB` (219 entries, real `conf/` + `db/`), minio
`54 MB → 133 MB` (183,220 entries), both from the correct live sources.

### Leftovers

- The empty orphan volume `homelab_questdb_data` was removed (0 files, referenced by no compose file
  and attached to no container).
- ⚠️ **`/opt/homelab/data/minio/data` (16 GB) is still on disk** — the stale pre-tiering object store,
  untouched since 2026-06-29. Deliberately **not** deleted: it is 16 GB of old objects that nobody has
  confirmed is redundant. Verify it against `/srv/ai-data/object-store` before reclaiming the space.

### Lesson for any new component

Never hardcode a host path or volume name in `backup.sh`. Resolve it from the running container, and
make the archive prove it captured something. A backup that reports success while containing nothing
is strictly worse than one that fails loudly — it consumes the trust you'd otherwise spend checking.

## `neo4j-example` graph — backup + a DR prerequisite (2026-07-20)

The `research-app` desk's dedicated graph store (`neo4j-example`, todos #31) is backed up
nightly (`backup_neo4j_research` → `neo4j-example-*.tar.gz`) and restore-verified weekly
(`verify_neo4j`). It's a **rebuildable projection** of the Postgres graph SoR, so the tar is a
fast-restore convenience; the authoritative recovery is a `graph.edges` replay from Postgres.

**Why it's a bind mount, not a named volume** — and the trap it dodges: a named volume lands under
`/var/lib/docker/volumes` (root `0700`), which the nightly backup, running as the non-root `homelab`
user, **cannot stat** — so `tar_host_dir`'s `[ -d "$src" ]` guard hard-fails. A `/srv/ai-data` bind
mount is group-traversable, so the backup works (and it keeps DB data off the nvme root, per the
tiering plan). The container runs as root, so the dir may be root-owned.

**DR prerequisite:** the host dir must exist before the container starts. On a rebuild:
```bash
sudo mkdir -p /srv/ai-data/graph/neo4j-example
sudo chown root:homelab /srv/ai-data/graph /srv/ai-data/graph/neo4j-example
sudo chmod 2775 /srv/ai-data/graph /srv/ai-data/graph/neo4j-example
```
The `research` **Postgres** db, the `research-artifacts` **MinIO** bucket, and the
`research_dial_*` **QuestDB** tables need no new backup component — they're captured by the existing
`pg_dumpall` / MinIO tar / QuestDB tar respectively. Qdrant and Redis are expendable projections/cache.
